CallMeMaybe

Reliable function calling with a 0.6B-parameter LLM that runs on a laptop.

role
solo, 42 curriculum
stack
Python, numpy, pydantic, Qwen3-0.6B
result
100% valid JSON, up from about 33% by prompting
source
github.com/sucamchi/CallMeMaybe

Given "What is the sum of 40 and 2?" and a catalog of functions, the program doesn't answer "42". It answers with the call that would: {"name": "fn_add_numbers", "parameters": {"a": 40, "b": 2}}. Small models are bad at this. Asked politely for JSON, this one produced something parseable about a third of the time.

So I stopped asking politely. A model scores every token in its vocabulary (151,936 of them) and the best score wins. Constrained decoding adds one step in between: every token that would break the output gets a score of minus infinity, so it can never win. The model still makes the choices, but only among options that are allowed.

The hard parts

  • Picking a function without building a mask. All the names are tokenized and walked side by side. At each step the model only chooses among the next tokens of names still in the race, so it can't invent a function. Where every survivor agrees, the model isn't called at all.
  • Numbers have no "end" token. Strings stop at their closing quote, but every token in the number mask continues the number. The trick: also look at what the model would pick without the mask. The moment that's a comma or a brace, the number is finished.
  • "Number-shaped" isn't enough. 1, . and 2 are all number characters, but 1.2. isn't a number. Each candidate is also checked by a small state machine for the JSON number grammar.
  • I'd never touched an LLM before. Tokenizers, logits, byte-level vocabularies: I learned them from articles, experiments and the SDK's source code, because its documentation was thin.

Numbers

11 prompts, 6 functions, a laptop GPU: every output is valid and correctly typed, the right function is picked every time, and 80 to 90% of argument values are right. 97% of the runtime is the model's 109 forward passes. The decoding logic costs almost nothing.

Fly-in

Route a whole fleet of drones through a network in as few turns as possible.

role
solo, 42 curriculum
stack
Python, heapq, pygame, mypy
result
every test map under target; 25 drones in 43 turns (target 45)
source
github.com/sucamchi/Fly-in

Zones have capacities and costs, drones can't share a full zone, and everyone must reach the goal. The obvious plan, a route per drone, falls apart in traffic: routes planned in advance don't know about congestion that hasn't happened yet.

So I turned it around. Dijkstra runs once, backwards from the goal, giving every zone a "turns remaining" number. After that, no drone owns a route. Each turn, each drone just steps to the neighbouring zone with the lowest number that still has room, or waits.

Why it can't deadlock

  • A drone only ever moves to a zone with a strictly lower number. Its number falls every move, so it can't loop or bounce back and forth.
  • Drones move nearest to the goal first. The nearest drone's next zone can only be blocked by drones even nearer, and those have already moved this turn. So at least one drone moves every turn and the fleet always makes progress.

Because of that guarantee, a turn where nothing moves can only mean a bug, so the engine raises an error instead of hanging. The demo above runs the same rules in JavaScript, with tests.

Codexion

The dining philosophers problem in C, with real threads and two scheduling policies.

role
solo, 42 curriculum
stack
C, POSIX threads, mutexes, condition variables
result
deadlock-free by construction; FIFO and earliest-deadline-first
source
github.com/sucamchi/Codexion

Coders sit around a table with one USB dongle between each pair. Compiling needs both neighbouring dongles at once, each dongle needs a cooldown after use, and a coder who goes too long without compiling burns out and ends the run. Every coder is a thread, and a monitor thread watches for burnout.

Drag the burnout time down to about 400 ms and watch the schedule fall apart.

How it stays alive

  • Lock ordering. Odd-numbered coders take their left dongle first and even-numbered coders their right. That breaks the circle where everyone holds one dongle and waits forever for the other.
  • Fair queues. Each dongle keeps a tiny priority queue of waiting coders. FIFO serves the oldest request, and EDF serves whoever is closest to burning out.
  • A synchronised start. All threads wait on a condition variable until everyone is ready, so nobody gets a head start.
  • Clean shutdown. When someone burns out, the monitor raises a stop flag and wakes every sleeping thread so they can exit, then main joins and frees everything.

The part I'm proudest of is the reasoning about what doesn't need a lock. The stop flag only ever goes from 0 to 1, and each progress counter has exactly one writer, so reading them unlocked is safe. The README writes that argument out instead of hiding it.

A-Maze-ing

A maze generator and solver with an interactive terminal UI, shipped as a pip package. Fig. 0 at the top of this page is a port of it.

role
team of 2: architecture, generation, display, packaging
stack
Python, ANSI terminal UI, build, flake8, mypy
result
perfect mazes and Pac-Man boards; reusable mazegen package
source
github.com/sucamchi/A-Maze-ing

It reads a config file, carves a random maze with depth-first search (an explicit stack, so big mazes don't hit Python's recursion limit), solves it with breadth-first search, and draws it in the terminal with colours, a show/hide solution toggle and a step-by-step generation animation. Each cell is one 4-bit number, one bit per wall, which keeps the grid tiny and made the hex output format trivial.

I set up the architecture and tooling (flake8 and mypy from the first commit), wrote the generator core, the terminal display and the animation, and packaged it. My teammate wrote the solver, the output format and the Pac-Man mode. We worked on separate branches and kept main working the whole time.

Lesson learned: embedding a "42" pattern of solid cells into a random maze looked like an afternoon's work. It was not.

OcupaSol

Forecasting hotel occupancy on the Costa del Sol, 12 months ahead, from official data.

role
team of 3: I owned the data and the model
stack
Python (standard library), JavaScript, ridge regression
result
2,035-row dataset; model backtested on 36 unseen months
source
github.com/sucamchi/OcupaSol

Hotels here swing from about 45% full in winter to over 80% in August, and many still plan staff and prices by copying last year. That's the baseline to beat. I wrote a script that pulls the official monthly survey from the INE (Spain's statistics office) API and builds the dataset above: 2,035 monthly records for the coast and seven towns, back to 1999, with real gaps left as gaps.

The model starts from "same month last year" and learns how to correct it from the recent year-on-year trend, with a ridge regression solved in plain JavaScript in the browser, no ML library. COVID months are left out of training. It's backtested on the last three years against the naive baseline, and the app shows its real error and a 90% interval instead of one overconfident number.
